# atlas-mcp

The `atlas` MCP service: an MCP server that lets an agent work with Atlas through tools instead of
raw HTTP. It is FastAPI hosting a FastMCP streamable-HTTP app, with no build step and one Docker
image. It holds no rules and no token of its own: every call reaches atlas-api with the token of
the caller that made it, and atlas-api decides what that caller may read and write.

For installing and running the whole product, read the product documentation instead:

- [Install](../docs/oss/INSTALL.md) brings atlas-mcp up as part of the stack (`deploy/oss/`), with
  TLS, the optional gateway and the Claude Code connection.
- [Agents](../docs/oss/guides/agents.md) takes a person from an account to a working agent.
- [MCP tools](../docs/oss/MCP-TOOLS.md) lists every tool, its parameters and its description
  (generated by `tools/gen_tool_ref.py`).
- [Configuration](../docs/oss/CONFIG.md) lists every setting and its default.

This page is for whoever changes the service itself.

## What's here

```
mcp/

  docker-compose.yml       a standalone compose project: atlas-mcp on 127.0.0.1:8092 (plain HTTP, loopback)
  docker-compose.tls.yml   atlas-mcp-tls: a Caddy HTTPS door on :8446 for the standalone project
  requirements.txt         pinned per ADR 0006 (mcp stays on 1.x; see the comment there)
  .env.example             every setting this service reads, commented
  app/
    main.py                FastAPI host: /health, mounts FastMCP at /mcp/
    mcp_server.py          FastMCP("atlas", ...), the tool registry, transport security
    caller_auth.py         the 401 gate on /mcp/: a valid caller token or nothing
    client.py              the atlas-api HTTP client; forwards the caller's token
    tls.py                 https-only base URL, CA bundle, optional client certificate
    oauth_resource.py      RFC 9728 metadata and the 401 challenge, when OAuth is on
    envelope.py            the uniform {"ok": ...} tool envelope
    descriptions.py        every tool's short description (size-budgeted)
    tools_*.py             the tool surface: read, graph writes, work items, comments, setup
    settings.py            the settings and their defaults
  verify_*.py              self-contained checks; most stub atlas-api, the *_api ones need a real one (CI)
```

## Caller authentication: every caller is itself

Every request to `/mcp/` must carry the caller's own service token:

```
Authorization: Bearer atlas_svc_...
```

- **No header, a malformed one, or a token atlas-api does not accept: HTTP 401** with
  `WWW-Authenticate: Bearer`, from `app/caller_auth.py`, before FastMCP sees the request. No
  session is created and no tool runs. If atlas-api cannot be reached to check, the answer is 503,
  never a pass.
- **The gate asks the API, it does not decide.** It calls `GET /api/me` with the presented token
  and lets the request in on a 200 (cached 60 s by SHA-256 of the token, `ATLAS_MCP_AUTH_CACHE_S`).
- **Every tool call is made with the token of the HTTP request that carried it** (`app/client.py`),
  per MCP message rather than per session. atlas-api applies that caller's scopes and grants, and
  the audit log records that credential and the person behind it (ADR 0034).
- **Destructive tools are the API's call, per caller.** The delete tools hit `DELETE` routes, which
  cost the `admin` scope; writes cost `write`. `ATLAS_MCP_ENABLE_DELETE` only decides whether
  `atlas_delete` is offered; it grants nothing.
- **No token is ever logged** or put into an error message, by the gate or the client.

A person mints an agent credential on the board (Settings, agent credentials), or an operator mints
one with `atlas-admin token mint` ([Install, section 7](../docs/oss/INSTALL.md)). Mint per agent
and per purpose, narrowly: `read` for an agent that only looks, `read,write` for one that files and
updates work, `admin` only where it must delete.

**IdP access tokens (opt-in, ADR 0041 §9).** With `ATLAS_OAUTH_RESOURCE` (the same value atlas-api
reads) and `ATLAS_OIDC_ISSUER` set, atlas-mcp serves the OAuth protected-resource metadata at
`/.well-known/oauth-protected-resource[/mcp]` and its 401s carry
`WWW-Authenticate: Bearer resource_metadata="..."`, so an MCP client can sign in at the IdP and
present that access token. atlas-api still validates it. Unset: no route, and the 401 is unchanged.

**Migration fallback (off by default).** `ATLAS_MCP_ALLOW_SHARED_TOKEN=1` with `ATLAS_TOKEN` lets a
request that sends **no** Authorization header act as that one shared token, so an install that
used one can move its clients over one at a time. It warns at startup and never sends a DELETE; a
request that presents a token always acts as itself.

## Transport security

- **Allowed hosts.** DNS-rebinding protection is on: a request whose `Host` is not on
  `ATLAS_MCP_ALLOWED_HOSTS` gets **421**, one whose `Origin` (if it sends one) is not on
  `ATLAS_MCP_ALLOWED_ORIGINS` gets 403. Set your install's public name there (`.env.example`);
  `deploy/oss/.env.example` shows the full list for the stack. The protection cannot be turned off.
- **Session idle timeout.** Streamable-HTTP sessions idle for **4 hours** are closed; the client
  re-initializes.

## Talking to atlas-api

`app/client.py` is the only place this service calls out. `ATLAS_BASE_URL` is **required, with no
default**: the process exits at import time naming it. It must be `https://` with a certificate
that verifies; `app/tls.py` refuses a plain `http://` URL to anything but loopback at startup.

- In the stack (`deploy/oss/`) the value is `https://atlas-api:9443`: on atlas-mcp's internal
  network that name belongs to `atlas-tls`, the stack's Caddy, which proxies over HTTPS to
  atlas-api. atlas-mcp shares no network with atlas-api, so it has no plain-HTTP route to it at all.
- `ATLAS_CA_BUNDLE` replaces the system trust store with exactly the CA certificates in that PEM
  file (the install CA, or an enterprise root). A missing file stops startup.
- Optional mTLS on that hop: `ATLAS_MCP_CLIENT_CERT_FILE` and `ATLAS_MCP_CLIENT_KEY_FILE` (both or
  neither, checked at startup), matched by `ATLAS_TLS_CLIENT_AUTH=require` on the stack's front. It
  is a network identity beside the Bearer token, never instead of it.

The client sends the caller's `Authorization: Bearer <token>` only, no cookie and no `Origin`, and
never follows redirects. Atlas's `{"error", "detail", "field"}` error bodies become the tool
envelope's `error.type` and `error.message`.

## TLS

Every hop that carries a Bearer token is HTTPS with the certificate verified. Plain HTTP exists only
on loopback or inside one compose network, where the token never reaches a wire.

```
client --https--> atlas-tls (/mcp, or :9444 for the gateway) --https--> atlas-mcp
atlas-mcp --https--> atlas-tls :9443 (as atlas-api) --https--> atlas-api
```

The standalone compose project in this directory binds `:8092` to loopback and puts a Caddy door
(`docker-compose.tls.yml`) in front, whose certificate comes from `ATLAS_MCP_TLS_MODE`, one of
`deploy/caddy/tls/*.caddy`: `files` (your PKI: `tls.crt` and `tls.key` in `ATLAS_MCP_TLS_CERT_DIR`),
`internal` (Caddy's own CA) or `acme-cloudflare` (Let's Encrypt by DNS-01).
`tools/ci/check_tls.sh` fails the build on a plain `http://` URL to a non-loopback host, a
non-loopback publish of a plain-HTTP token port, or any switch that turns verification off.

## Running it

Locally, without Docker, against an atlas-api you can reach over HTTPS:

```bash
cd mcp
pip install -r requirements.txt
ATLAS_BASE_URL=https://atlas.example.com python -m uvicorn app.main:app --host 127.0.0.1 --port 8092
```

`GET /health` answers `{"status": "ok"}` without a token. Everything under `/mcp/` needs one.

## Changing it

- **No `from __future__ import annotations`** in any module where a tool function is defined:
  FastMCP inspects a tool's real signature to build its JSON Schema.
- FastMCP is built with `streamable_http_path="/"`, so the endpoint is `/mcp/` and not `/mcp/mcp/`,
  and its session manager starts in the FastAPI lifespan (`app/main.py`).
- **Do not keep a tool roster in this file.** `tools/list` on the running server is the register,
  and `docs/oss/MCP-TOOLS.md` is generated from the code.
- A tool's description lives in `app/descriptions.py` and stays within the budgets that
  `verify_tool_descriptions.py` enforces.
- `atlas_tree` deliberately asks for less than `GET /api/graph`: it requires `focus`, turns the
  `prose`, `work` and `meta` tiers off, and asks the API to refuse rather than cut off. The limits
  are enforced in `backend/`; this service only chooses what to send (`verify_atlas_tree.py`).
- No tool sets a work item's assignee: `atlas_update_work` exposes `status`, `result`, `body`,
  `acceptance`, `depends_on` and `binding`. Reassign through the board or the REST API. Assignment
  is not a grant: a hidden item stays hidden from its assignee.

## Checks

Each `verify_*.py` is a standalone script: `python mcp/verify_<name>.py`, exit status 0 on success.
The ones ending in `_api.py` start against a real atlas-api and Postgres, which CI provides; the
rest stub atlas-api in process. They are not in `backend/verify_all.py`, which discovers `backend/`
only; CI runs them in the `mcp` job.
